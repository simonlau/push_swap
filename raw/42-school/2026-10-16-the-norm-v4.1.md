# Chapter I — Foreword

The norminette is a Python and open source code that checks Norm compliance of your source code. It checks many constraints of the Norm, but not all of them (eg. subjective constraints). Unless specific local regulations on your campus, the norminette prevails during evaluations on the controlled items. In the following pages, rules that are not checked by the norminette are marked with *(*)*, and can lead to project failure (using the Norm flag) if discovered by the evaluator during a code review.

Its repository is available at https://github.com/42School/norminette.

# Chapter II — Why?

The Norm has been carefully crafted to fulfill many pedagogical needs:

- **Sequencing**: coding implies splitting a big and complex task into a long series of elementary instructions. Cryptic language syntaxes that do multiple instructions apparently at the same time are confusing. The Norm asks you to create simple pieces of code, where the unique task of each piece can be clearly understood and verified. That's why 25 lines maximum in functions, and why for, do..while, or ternaries are forbidden.
- **Look and Feel**: while exchanging with friends and workmates during peer-learning and peer-evaluations, you do not want to spend time to decrypt their code. The Norm provides instructions for naming, indentation, brace rules, tabs and spaces. This allows you to smoothly have a look at other's codes that will look familiar.
- **Long-term vision**: making the effort to write understandable code is the best way to maintain it. The sooner you learn to do so, the better.
- **References**: the rules are not arbitrary — they are based on established best practices.

# Chapter III — The Norm

### III.1 Naming

- A structure's name must start by `s_`.
- A typedef's name must start by `t_`.
- A union's name must start by `u_`.
- An enum's name must start by `e_`.
- A global's name must start by `g_`.
- Identifiers (variables, functions, user defined types) can only contain lowercases, digits and `_` (snake_case). No capital letters.
- Files and directories names can only contain lowercases, digits and `_` (snake_case).
- Characters that aren't part of the standard ASCII table are forbidden, except inside literal strings and chars.
- *(*)* All identifiers names should be explicit, or a mnemonic, readable in English, with each word separated by an underscore.
- Using global variables that are not marked `const` or `static` is forbidden, unless the project explicitly allows them.
- The file must compile. A file that doesn't compile isn't expected to pass the Norm.

### III.2 Formatting

- Each function must be at most **25 lines** long, not counting the function's own braces.
- Each line must be at most **80 columns** wide, comments included. A tabulation counts as the number of spaces it represents.
- Functions must be separated by an empty line.
- Indent code with **4-char-long tabulations** (ASCII char number 9), not spaces.
- Blocks within braces must be indented. Braces are alone on their own line, except in declaration of struct, enum, union.
- An empty line must be empty: no spaces or tabulations.
- A line can never end with spaces or tabulations.
- Never two consecutive empty lines. Never two consecutive spaces.
- Declarations must be at the beginning of a function.
- All variable names must be indented on the same column in their scope.
- The asterisks that go with pointers must be stuck to variable names.
- One single variable declaration per line.
- Declaration and initialisation cannot be on the same line, except for global variables (when allowed), static variables, and constants.
- In a function, place an empty line between variable declarations and the rest of the function. No other empty lines are allowed in a function.
- Only one instruction or control structure per line.
- An instruction or control structure can be split into multiple lines when needed. Following lines must be indented; operators go at the beginning of the new line.
- Each comma or semi-colon must be followed by a space (unless end of line).
- Each operator or operand must be separated by one and only one space.
- Each C keyword must be followed by a space, except for type keywords (int, char, float, etc.) and sizeof.
- Control structures (if, while..) must use braces, unless they contain a single instruction on a single line.

### III.3 Functions

- A function can take **4 named parameters** at most.
- A function that doesn't take arguments must be explicitly prototyped with `void`.
- Parameters in functions' prototypes must be named.
- You can't declare more than **5 variables** per function.
- Return of a function has to be between parenthesis, unless the function returns nothing.
- Each function must have a single tabulation between its return type and its name.

### III.4 Typedef, struct, enum and union

- Add a space between `struct` and the name when declaring a struct. Same for enum and union.
- Inside the braces of struct, enum, union, regular indentation rules apply.
- Add a space after `typedef`, and apply regular indentation for the new defined name.
- Indent all structures' names on the same column for their scope.
- You cannot declare a structure in a .c file.

### III.5 Headers (include files)

- *(*)* Allowed elements of a header file: header inclusions, declarations, defines, prototypes and macros.
- All includes must be at the beginning of the file.
- You cannot include a C file in a header file or another C file.
- Header files must be protected from double inclusions. If the file is `ft_foo.h`, its bystander macro is `FT_FOO_H`.
- *(*)* Inclusion of unused headers is forbidden.
- Header inclusion can be justified in the .c file and in the .h file itself using comments.

### III.6 The 42 Header

- Every .c and .h file must immediately begin with the standard 42 header: a multi-line comment with special format including creator login and student email (@student.campus), date of creation, login and date of last update.
- *(*)* The 42 header must contain up-to-date information. Each time the file is saved on disk, the information should be automatically updated.

### III.7 Macros and Pre-processors

- *(*)* Preprocessor constants (#define) must be used only for literal and constant values.
- *(*)* All #define created to bypass the norm and/or obfuscate code are forbidden.
- *(*)* You can use macros available in standard libraries, only if those are allowed in the scope of the given project.
- Multiline macros are forbidden.
- Macro names must be all uppercase.
- Indent preprocessor directives inside #if, #ifdef or #ifndef blocks.
- Preprocessor instructions are forbidden outside of global scope.

### III.8 Forbidden Stuff

- `for`
- `do...while`
- `switch`
- `case`
- `goto`
- Ternary operators such as `?`
- VLAs (Variable Length Arrays)
- Implicit type in variable declarations

### III.9 Comments

- Comments cannot be inside function bodies. Comments must be at the end of a line, or on their own line.
- *(*)* Comments should be in English, and useful.
- *(*)* A comment cannot justify the creation of a carryall or bad function.

### III.10 Files

- You cannot include a .c file in a .c file.
- You cannot have more than **5 function-definitions** in a .c file.

### III.11 Makefile

- The `$(NAME)`, `clean`, `fclean`, `re` and `all` rules are mandatory. The `all` rule must be the default one.
- If the makefile relinks when not necessary, the project will be considered non-functional.
- In a multibinary project, you must have a rule for each binary. The "all" rule will compile all binaries.
- In a project that calls a function from a non-system library (e.g., libft) that exists along your source code, your makefile must compile this library automatically.
- All source files needed to compile your project must be explicitly named in your Makefile. No "*.c", no "*.o", etc.
